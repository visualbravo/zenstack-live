## This Project is in Beta

There are still some things missing or broken. Please [open an issue](https://github.com/visualbravo/zenstack-live/issues) if you run into something that isn't listed here.

## Column Types

`DateTime` and `Decimal` work with every column type that ZenStack can map them to, with or without a native type attribute, but there are two exceptions:

- `Decimal[] @db.Money` is always `[]`, because Debezium doesn't capture `MONEY[]` columns.
- A `DateTime` that's `infinity` or `-infinity` in Postgres is an `Invalid Date`, because a `Date` can't represent it.

## Field Mapping

`@@map` and `@@schema` on a model work without any configuration. `@map` on a field doesn't. Events are keyed by column name, and LIVE reads them by field name, so a mapped field comes through as `null`, and its value ends up under the column's name, which isn't in the type:

```prisma
model User {
  id        String @id
  firstName String @map("first_name") // Always `null` in events, and in filters.
}
```

Enum values that use `@map` likewise arrive as their database value, and not their name in your schema.

## Postgres Only

Actually, that might not be totally true. Debezium has MySQL support, but this project has not been tested with it. Want to help? Give it a try and tell us how it goes.

## Events Are Snapshots

An event represents one record at one moment. If you're listening to `created` events, the record might not exist in the database anymore if it was deleted before your handler processed it. Use [`event.date`](/docs/guides/events#timing) to see when a change was processed.

## No Relation Queries

You can't filter on relations, and relations aren't included in events. Although that would be very cool, an event is a snapshot of one row, so there's nothing reliable to compare against. Computed fields are unavailable for the same reason. See [What Events Don't Contain](/docs/guides/events#what-events-dont-contain).

## Filter Differences

Filters are validated by ZenStack and follow the same semantics as a query, including how nulls behave, but they're evaluated in JavaScript, not by Postgres. So:

- `$expr`, `fuzzy`, `fts`, computed fields, and `Json` paths with filter expressions or `.**` aren't supported.
- Strings are ordered by code unit, and not by your database's collation.
- Timestamps are compared to the millisecond.

## Events Are Kept for 24 Hours

Every stream on a model reads the same events, so they're removed by age, not when they're consumed. A stream that's offline for longer misses what it didn't read, and events waiting to be retried are dropped. [Set `retention`](/docs/deployment/retention) to change this.

## No Serverless Hosting

Stream handlers need to be constantly waiting for new events to come in. Your main backend can still be serverless, and you just [communicate between the two](/docs/recipes/forwarding-to-serverless) like any other service.

## History Isn't Captured

Changes made before a table's first stream aren't captured. Once a table has a stream it stays captured, even while nothing is running, until you [remove it](/docs/deployment/pruning#removing-streams). A new stream on an already captured table also starts from new events, and doesn't replay what's in Redis.
